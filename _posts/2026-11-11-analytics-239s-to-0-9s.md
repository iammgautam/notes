The slowest report on our spend analytics screen took 239 seconds. It was a twelve-month supplier diversity report with one extra column: for each supplier, what its diversity classification was *before* the current one. Four minutes is not a report. It is a reason to export everything to a spreadsheet and never come back.

A teammate got it to 0.9 seconds with one index: no query rewrite, no new infrastructure, no change in output. Why one index was enough only makes sense once you see the system around it, which I work in and extend: a monthly rollup, a deliberately large set of indexes, and a cache in front of the report generator.

## What spend analytics is for

Gainfront makes supplier lifecycle management software for procurement teams. A client loads its accounts-payable data, one row per invoice line it paid, and asks questions like "how much did we spend with women-owned suppliers last year, by quarter?" or "which categories have the most minority-owned spend, by business unit?". The answers go into supplier diversity reports, budget reviews and supplier negotiations.

## The constraints that shaped everything

- **Reports are ad hoc.** The user picks the group-by fields, filters, date range and period columns. There is no fixed list of queries to tune.
- **Rows are wide.** An invoice line has around a hundred descriptive columns, and each client uses a different subset.
- **Data arrives in batches.** A client loads a new file weekly or monthly. Between loads, the numbers do not change.
- **No new infrastructure.** Each client runs as its own deployment. An OLAP database or a search cluster per client is too much to operate, so everything lives in the PostgreSQL that is already there.

The batch constraint is the lever. If data only changes when a file is loaded, we can do expensive work once per load and reuse it for every report until the next one.

```text
  invoice file (millions of lines)
        |
        v
  +---------------+   once per load:
  | invoice lines |   INSERT ... SELECT ... GROUP BY dims, month
  +-------+-------+
          |
          v
  +---------------+        miss: one pivot query      +---------------+
  | monthly       | ------------------------------->  | cached report |
  | rollup        |                                   | lines (JSONB, |
  | (56 indexes)  |                                   | tsvector+GIN) |
  +---------------+                                   +-------+-------+
                                                              ^
  report request -> allow-list -> canonical key -> hit? ------+
  page / sort / search inside a report -----------------------+
```

## Layer 1: one row per combination per month

Reports never read raw invoice lines. They read a precomputed rollup: one row per unique combination of dimensions per month, with the amounts summed.

- **The grain is a month.** Every report period is a whole number of months, so a finer grain would only add rows no report can use.
- **Dimensions are never NULL.** Text becomes `''`, booleans false, arrays empty. `NULL = NULL` is not true in SQL, which makes NULLs awkward in GROUP BY, filters and indexes. It is also why the partial indexes later can say `<> ''`.
- **Code and description pairs are flattened** into one label like `4410 : Office supplies`. Grouping by one column is cheaper than grouping by two.
- **The insert is ordered by month.** Readers never see table order, so this looks pointless. It exists for the BRIN index below.

This is the CQRS read-model idea in plain SQL: the invoice table is shaped for loading, the rollup for reading. The costs are real. Reports show data as of the last refresh, and with so many grouping keys the rollup is smaller than the raw table but not by orders of magnitude. The statement is also generated from per-client configuration, with the column list, select list and GROUP BY matched by position, so a test exists only to check that those lists line up. One column out of place would silently write a wrong value into every row.

### Swapping in a new version without blocking readers

The rollup started as a materialized view, then became a table rebuilt with `TRUNCATE` and `INSERT`, whose exclusive lock stalled reports during every rebuild. The current design is a shadow write. A simplified version:

```sql
BEGIN;

INSERT INTO spend_rollup (generation, supplier_id, category,
                          diversity_class, month, amount)
SELECT 'b7e1', supplier_id,
       COALESCE(category, ''),
       COALESCE(diversity_class, ''),
       date_trunc('month', invoice_date)::date,
       SUM(amount)
  FROM invoice_lines
 GROUP BY 2, 3, 4, 5
 ORDER BY 5;                 -- physical month order, for BRIN

DELETE FROM spend_rollup WHERE generation <> 'b7e1';

COMMIT;
-- only now: tell listeners the rollup changed
```

MVCC does the rest. Until the commit, every reader sees the complete old set. After it, every new query sees the complete new set. There is never a half-built table, and no lock that blocks a reader.

```text
  refresh   BEGIN   INSERT gen B .... DELETE gen A   COMMIT   notify
  (worker)                                             |        |
  report 1    |---- sees gen A only -----|             |        |
  report 2                     |---- sees gen A only -------|   |
  report 3                                             |-- sees gen B
                                                                |
                                     report caches cleared <----+
```

The bill: briefly two full copies, dead tuples for VACUUM, and every inserted row updating every index. It all runs on a worker once per load, never in a request. And the "rollup rebuilt" notification fires after the commit on purpose. Listeners clear caches. If they ran inside the transaction, a report could be recomputed from the old rows and cached, and the commit would leave that cache stale with nobody left to clear it.

## Layer 2: 56 indexes, most of them boring on purpose

The rollup carries 56 indexes, added by many of us over four years: 53 B-trees, 2 GINs and 1 BRIN, five of them partial and two composite.

- **Single-column B-trees on filter columns.** We cannot predict which filter a user picks, and a composite index only helps queries that filter on its leading column. One index per common filter lets the planner pick the most selective, or combine two with a `BitmapAnd`.
- **BRIN on the month.** BRIN stores only the min and max for each range of pages, so it is tiny, and a date-range query skips every range that cannot overlap. It only works when values follow the physical row order, hence the ordered insert.
- **GIN on array columns.** A supplier can hold several diversity classifications. "Has WBE" (a women-owned business enterprise) is `classes @> '{WBE}'`, which a B-tree cannot answer. GIN maps each element to the rows that hold it.
- **Partial indexes for "is not null".** A value filter never matches NULL, so leaving NULLs out keeps the index small and in memory.

```sql
CREATE INDEX spend_rollup_month_brin
    ON spend_rollup USING brin (month);

CREATE INDEX spend_rollup_classes_gin
    ON spend_rollup USING gin (classes);

CREATE INDEX spend_rollup_parent_idx
    ON spend_rollup (parent_supplier_id)
    WHERE parent_supplier_id IS NOT NULL;
```

Every index makes every inserted row more expensive, and a refresh inserts the whole table. We pay that once per load, on a worker, and win it back on every report. Because writes are batched, it is a good trade here. On a table with constant writes it would be a bad one.

## The 239-second query

### The field

A diversity report can show each supplier's *previous* classification: "this supplier is WBE now, what was it before?". The report builder computes it with a correlated subquery. A simplified version of what the ORM generates:

```sql
SELECT r.supplier_id, r.category,
       (SELECT p.diversity_class
          FROM spend_rollup p
         WHERE p.supplier_id = r.supplier_id
           AND p.month < r.month
           AND p.diversity_class <> ''
           AND p.diversity_class <> r.diversity_class
         ORDER BY p.month DESC
         LIMIT 1) AS previous_class,
       SUM(r.amount) AS total
  FROM spend_rollup r
 GROUP BY r.supplier_id, r.category, previous_class;
```

In words: for this row's supplier, find the latest earlier row whose class is not blank and differs from mine.

### Three problems that multiply

1. **It ran once per input row, not once per output row.** The ORM puts the annotated subquery into the GROUP BY, so PostgreSQL evaluates it for every row before grouping: hundreds of thousands of runs for one report on a large client.
2. **Each run used two indexes and then the heap.** The planner combined the single-column supplier and month indexes with a `BitmapAnd`, then visited heap pages to recheck the conditions and read the class.
3. **Most of what it read was thrown away.** The large majority of rows had a blank class and were discarded by `<> ''` after being fetched.

Runs × pages per run × wasted fraction. `EXPLAIN (ANALYZE, BUFFERS)` showed tens of millions of shared-buffer hits for one report, nearly all from memory. The query was not waiting on disk. It was busy doing work that produced nothing.

### The fix: one index with three properties

```sql
CREATE INDEX spend_rollup_prev_class_idx
    ON spend_rollup (supplier_id, month, diversity_class)
    WHERE diversity_class <> '';
```

| Property | What it does | Cost removed |
|---|---|---|
| Composite, supplier then month | Jump to the supplier, walk months backwards, stop at the first match | The `BitmapAnd` |
| Class in the index key | Everything the subquery needs is in the index: index-only scan | The heap visits |
| Partial: `WHERE class <> ''` | Blank rows are not in the index at all | Reading rows only to drop them |

```text
  BEFORE, per input row               AFTER, per input row
  ---------------------               --------------------
  Bitmap Index Scan (supplier) -+     Index Only Scan Backward
  Bitmap Index Scan (month)    -+       on (supplier, month, class)
          BitmapAnd                     WHERE class <> ''
  Bitmap Heap Scan                    jump to supplier, walk months
    recheck, filter class <> ''         down from "before mine",
    (discards most rows)                stop at first different class
  take the latest
```

Two details are easy to get wrong when explaining this. "Covering" here does not mean an `INCLUDE (...)` clause: the class is a key column, which also sorts it within each supplier and month at no cost. And the partial condition works only because it is written *exactly* as the subquery filters. The planner uses a partial index only when it can prove the query's `WHERE` implies the index's condition. `class <> ''` against `class <> ''` is a trivial proof. Write the query as `length(class) > 0` and the planner silently ignores the index.

### Why it is safe

An index changes how rows are found, not which rows match. The one place it could matter is `LIMIT 1`: if two rows shared a supplier and month but had different classes, a new access path could pick a different "latest" row. My teammate checked that no supplier and month pair holds more than one distinct non-blank class, so there is exactly one answer.

### Why we did not rewrite the query

`LAG(class) OVER (PARTITION BY supplier_id ORDER BY month)` computes "previous" in one pass and looks like the textbook fix. The reasons against it are about the system, not the SQL:

- The report builder composes queries from user choices. The subquery is one optional column. A window function changes the shape of the whole query.
- The index is a migration with zero code change and zero output change, and it rolls back with one `DROP INDEX`.
- The same subquery lives in the older report UI too. One index fixed both.

### Results

The field went from **239 seconds to 0.9 seconds** for a twelve-month report, and another run of the same change came in under half a second. Its twin field, the classification at each transaction's date, got a matching index and dropped by about two orders of magnitude. Buffer hits fell by more than 100×, which is the number I trust more: time depends on cache state and hardware, page counts do not.

One caveat. An index-only scan skips the heap only for pages the visibility map marks all-visible. Right after a refresh, the new pages are not marked yet, so until autovacuum visits the table the scan does heap fetches again. It is still fast, because the index has already narrowed the work to one supplier. `Heap Fetches` in `EXPLAIN ANALYZE` shows when it happens.

## Layer 3: one pivot query, then cache-aside

The rollup makes one report cheaper. The cache makes the second view free.

Every requested field is first checked against a field catalog. The same catalog fills the UI dropdown, so the dropdown and the allow-list cannot drift, and no user-supplied name reaches a GROUP BY unchecked. Then a report with twelve monthly columns becomes one query with conditional aggregation instead of twelve queries:

```sql
SELECT supplier_name, category,
       SUM(amount) FILTER (WHERE month >= '2025-01-01'
                             AND month <  '2025-04-01') AS q1,
       SUM(amount) FILTER (WHERE month >= '2025-04-01'
                             AND month <  '2025-07-01') AS q2,
       -- ... one column per period
       SUM(amount) AS total
  FROM spend_rollup
 WHERE month >= '2025-01-01' AND month < '2026-01-01'
 GROUP BY supplier_name, category
 ORDER BY total DESC;
```

The ORM writes it as `SUM(CASE ...)`, which is the same thing. When each distinct value of a field becomes a column, the generator caps it at the top eleven values, because a field with thousands of values would otherwise make thousands of columns.

The result is cached as one header row per unique request plus one row per report line, holding the line as JSONB and a `tsvector` for search. JSONB fits because the user chooses the columns at run time. The key is canonical: drop paging and UI parameters, drop empty and `"null"` values, wrap scalars in one-item lists, serialize with sorted keys. Otherwise page 2 misses the cache page 1 built, and `supplier=5` and `supplier=[5]` become two entries.

The writer locks the header row (`SELECT ... FOR UPDATE`) before replacing the lines, so two users opening the same uncached report do not interleave rows. Paging, sorting and searching then run on one report's cached lines and never touch the rollup. Every refresh deletes all cached reports: working out which ones a load affected is hard, and loads are rare.

## My part of this path

### Four new dimensions on the rollup

I added the UNSPSC classification to the rollup. UNSPSC is the UN's product and service code, a strict four-level hierarchy: segment, family, class, commodity. I added a code and description per level on the invoice table, four flattened `code : description` columns on the rollup, the flattening in the query builder, a B-tree index per level, and the API side: choice endpoints, allowed filters and field details.

Why four single-column indexes and not one composite? Users filter at the level they care about. Someone looking at office equipment filters on the family and never mentions the segment, and a composite on all four levels only helps queries that start with the segment. And as long as the data respects the hierarchy, a commodity determines its class, family and segment, so the four new grouping keys do not split the rollup any finer than the commodity alone.

### An N+1 in the supplier analytics report

The supplier analytics report has one row per supplier and three certificate columns: the primary certificate, its expiry date, and a summary of all certificates. They were filled in Python, row by row: one certificate query per report row, and a second "find the primary one" query for two of the columns. N rows meant between N and 3N extra round trips.

I moved each column into the report's SQL as a correlated subquery, so the whole report became one statement:

```python
from django.db.models import OuterRef, Subquery

primary_cert = (
    Certificate.objects
    .filter(supplier_id=OuterRef("pk"), is_primary=True)
    .values("expires_on")[:1]
)

report = suppliers.annotate(
    primary_cert_expiry=Subquery(primary_cert),
)
```

The summary column became a grouped subquery with `string_agg`. I first added an explicit index on the certificate table's supplier column, then took it out: Django already indexes every foreign key, so the flag added nothing. The gain came from the query shape.

The two stories connect. Correlated subqueries were right for the N+1 because that report has one row per supplier and each subquery is one indexed lookup. The 239-second query is the same technique inside a large GROUP BY, where it runs per input row and needs an index shaped exactly for it.

## What I would change next

- **Compute "previous class" during the refresh.** The index made the per-row subquery cheap, but it still runs at report time. A `LAG()` inside the refresh, stored as a column, moves it to once per load, which is the point of a rollup.
- **Audit the 56 indexes.** The month has three indexes, one redundant, and some array columns carry a B-tree beside their GIN. `idx_scan = 0` in `pg_stat_user_indexes` on a busy client is the drop list, and each drop makes every refresh cheaper.
- **Lock the refresh explicitly.** Two overlapping refreshes could both insert before either deletes. A single worker serializes them today, but nothing in the code says so. A `pg_advisory_xact_lock` would make it a rule.
