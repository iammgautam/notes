The worst request I traced at MarsDevs made more than 500 database queries. None of them was slow. Almost all were small lookups by id, the kind that finish in a millisecond or two, so nothing in a slow-query log would ever point at them, and any single query you picked out looked perfectly healthy. Added together, they were a slow page.

When I was done with that request and the ones that looked like it, they made about 5 to 10 queries each. The fixes were not exotic: `select_related`, `prefetch_related`, and asking the database only for the columns the response used. The hard part was finding them, and then keeping them fixed.

I met the same bug again at Gainfront, in a report, where the right fix was a correlated subquery instead of a prefetch. Both are below, along with a separate piece of MarsDevs work where the problem was one slow query rather than hundreds of fast ones.

## Why five hundred fast queries make one slow page

The Django ORM is lazy. `order.customer` runs a query the first time you touch it, unless the customer was loaded together with the order. Inside a loop, one query for a list turns into one query for the list plus one per row, per relation. That is the N+1.

The cost is not database CPU. It is round trips. Every query pays network latency, a trip through the driver, and Python building model instances from the result. A millisecond each sounds like nothing until you multiply it by 500.

```text
One request, 100 open orders, 3 items each

  before
    SELECT orders ................................ 1
    SELECT customer WHERE id = ? ................. x100
    SELECT items WHERE order_id = ? .............. x100
    SELECT product WHERE id = ? .................. x300
                                                  -----
                                                   501
  after
    SELECT orders JOIN customers ................. 1
    SELECT items JOIN products
           WHERE order_id IN (...) ............... 1
                                                  -----
                                                     2
```

## The shape of the bug

Every N+1 I have fixed had the same shape: code that loads a list, then touches relations on each row. Here is a simplified version. Orders belong to a customer and have items, and each item points at a product:

```python
def order_list(request):
    orders = Order.objects.filter(status="open")[:100]   # 1 query
    data = []
    for order in orders:
        data.append({
            "id": order.id,
            "customer": order.customer.name,              # +1 per order
            "items": [
                {"product": item.product.name,            # +1 per item
                 "qty": item.quantity}
                for item in order.items.all()             # +1 per order
            ],
        })
    return JsonResponse({"orders": data})
```

For 100 orders with three items each, that is 1 + 100 + 100 + 300 = 501 queries. I ran this against a scratch database to make sure, and Django agrees with the arithmetic. Only the first line looks like a database call.

DRF serializers hide it even better. A nested serializer, or a `SerializerMethodField` that reads a relation, runs once per object, and the view never mentions a relation at all.

## Count first, then guess

You cannot fix what you are not counting. The tools I reach for:

- **django-debug-toolbar** in development. Its SQL panel shows the count and groups "similar" and "duplicated" queries. Hundreds of near-identical `SELECT ... WHERE id = %s` lines that differ only in the parameter are the N+1 signature.
- **Logging `django.db.backends` at `DEBUG`** locally. Noisy, but nothing hides.
- **Tracing in production**, where a request span with hundreds of tiny child database spans is hard to miss.
- **`CaptureQueriesContext`** when I want a number in a shell or a test:

```python
from django.db import connection
from django.test.utils import CaptureQueriesContext

with CaptureQueriesContext(connection) as ctx:
    client.get("/api/orders/")

print(len(ctx.captured_queries))
for q in ctx.captured_queries[:5]:
    print(q["sql"])
```

The habit matters more than the tool. On an endpoint that feels slow, I look at the query count before I look at anything else. One slow query shows up in the slow log. Five hundred fast ones show up only as a slow page.

## Fixing it with select_related, Prefetch and only()

`select_related` follows a `ForeignKey` or `OneToOneField` with a SQL `JOIN`, so the related object arrives in the same row. Use it for single-valued relations only. Joining a many-valued relation multiplies rows.

`prefetch_related` handles reverse foreign keys and many-to-many. It runs one extra query per relation with `WHERE ... IN (...)` and stitches the results onto each parent in Python.

```text
select_related("customer")            prefetch_related("items")

  one query, wider rows                 one extra query per relation

  SELECT o.*, c.name                    SELECT * FROM order_items
  FROM orders o                         WHERE order_id IN (1, 2, ... 100)
  JOIN customers c                                |
    ON c.id = o.customer_id                       v
                                        Python groups the items by
                                        order_id and fills each
                                        order's prefetch cache

  for: ForeignKey, OneToOne             for: reverse FK, ManyToMany
```

The string form, `prefetch_related("items__product")`, works, but a `Prefetch` object lets you shape the inner query: filter it, join inside it, and trim its columns. Put together:

```python
from django.db.models import Prefetch

items = (
    OrderItem.objects
    .select_related("product")
    .only("order_id", "quantity", "product__name")
)

orders = (
    Order.objects.filter(status="open")
    .select_related("customer")                  # JOIN, same row
    .only("status", "customer__name")            # skip notes, blobs
    .prefetch_related(Prefetch("items", queryset=items))
)[:100]
```

The loop stays exactly as it was. It now runs two queries: orders joined to customers, then items joined to products. I checked it with 5, 50 and 100 orders and the count stayed at 2. That flat line is the whole point. The count no longer depends on how many rows the page shows.

Fetching only the needed fields is the other half. A list endpoint that renders a name and a status does not need a `TextField` of notes or a large JSON column on every row. `only()` and `defer()` keep model instances but load fewer columns. `values()` and `values_list()` skip model instances entirely, which is cheaper still when all you do is build JSON. Django adds the primary key and the foreign keys it needs for the joins on its own.

> **Gotcha:** `only()` can make things worse. Read a deferred field on each instance and Django runs one query per row to load it, which is a brand new N+1. Defer only what the code path truly never reads.

Counts and totals belong in the database too. `len(order.items.all())` or a Python `sum()` over a relation, just to show a number, is replaced by `annotate(item_count=Count("items"))` in the same query. Stacking aggregates over two different multi-valued relations is a trap, which I come back to below.

### Ways a prefetch silently stops working

- **Building a new queryset from the relation.** `order.items.filter(quantity__gt=1)`, `.exclude()` or `.order_by()` ignore the prefetch cache and query again. Filter inside the `Prefetch` queryset instead, and use `to_attr` to store the filtered list under its own name.
- **Model properties and methods** that query a relation, called from a template or a serializer.
- **Serializer changes.** Someone adds a nested field, nobody updates the view's queryset, and the count jumps.

## The same bug at Gainfront, in a report

Gainfront makes supplier lifecycle management software for procurement teams. One thing those teams track is supplier certifications: an outside agency certifies that a supplier is, say, women-owned or minority-owned, and the certificate expires. A supplier report usually wants the primary certification, its expiry date and a summary of all of them, so someone can chase a renewal before it lapses.

In one of our analytics reports, those certification columns were filled in Python, row by row. For each row of the report, the code ran a query for the supplier's certifications, and two of the columns ran another query to find the primary one. A report with N rows made between N and 3N extra queries.

A prefetch would have cut that to a constant, but the values would still live in Python. I wanted them inside the queryset, as columns the database computes, so the report could sort, page and export them like any other column. Correlated subqueries do exactly that. A simplified version, with neutral names:

```python
from django.contrib.postgres.aggregates import StringAgg
from django.db.models import OuterRef, Subquery, Value
from django.db.models.functions import Concat

primary = (
    Certification.objects
    .filter(supplier=OuterRef("pk"), is_primary=True)
    .order_by("-expires_on")          # make "the first one" stable
)

all_certs = (
    Certification.objects
    .filter(supplier=OuterRef("pk"))
    .values("supplier")               # group by the outer key...
    .annotate(text=StringAgg(Concat("kind", Value(" / "), "agency"),
                             delimiter="; "))
    .values("text")                   # ...and return one column
)

report = report.annotate(
    primary_kind=Subquery(primary.values("kind")[:1]),
    primary_expires_on=Subquery(primary.values("expires_on")[:1]),
    cert_summary=Subquery(all_certs),
)
```

The whole report became one SQL statement, whatever the number of rows. The `values("supplier")` before the `annotate` is the trick that turns an aggregate into a grouped subquery that returns one value per outer row.

My first version also added an index on the certification table's supplier foreign key. I took it out before the change merged: Django already creates an index for every `ForeignKey` column unless you tell it not to, so the flag added nothing. The gain came from the query shape.

A correlated subquery is not free, though. PostgreSQL runs it once per outer row. On a page of 50 suppliers that is nothing. Inside a big `GROUP BY` over hundreds of thousands of rows it can become most of the query's cost, and the fix there is an index shaped exactly like the subquery's lookup. That is a story for another post.

## When it is one slow query, not five hundred fast ones

The other number from MarsDevs came from different work. A handful of heavy queries took roughly 15 to 25 seconds, and after rewriting them they took about 1 to 2. The tools were the plain ones: the Django ORM where it produced good SQL, raw SQL where it did not, and joins, subqueries and indexes. I no longer have those query plans, so the SQL below is a reconstruction of the patterns, not the original queries.

The method is always the same. Run `EXPLAIN (ANALYZE, BUFFERS)` on the real data size, read the plan from the inside out, and look for:

- a sequential scan over a big table that a filter then throws mostly away;
- a nested loop or subplan with `loops=` in the tens of thousands;
- row estimates that are wildly off from actual rows (stale statistics);
- a sort that spills to disk.

One pattern I keep seeing is the join fan-out. Joining two multi-valued relations to aggregate both multiplies rows, which makes the query slower and the numbers wrong at the same time:

```text
order 7 has 3 items and 2 payments

  orders JOIN items JOIN payments

  order  item  payment
  -----  ----  -------
    7     a      p1
    7     a      p2        6 rows for one order:
    7     b      p1          SUM(quantity) counts every item twice
    7     b      p2          SUM(amount) counts every payment 3 times
    7     c      p1
    7     c      p2
```

The fix is to aggregate each relation on its own. When the outer query returns a page of rows, a scalar subquery per relation is simple and fast, and an index that matches the filter and the sort lets PostgreSQL stop after 50 rows:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id,
       (SELECT SUM(i.quantity) FROM order_items i
         WHERE i.order_id = o.id) AS total_qty,
       (SELECT SUM(p.amount) FROM payments p
         WHERE p.order_id = o.id) AS total_paid
FROM orders o
WHERE o.account_id = 42
  AND o.status = 'open'
ORDER BY o.created_at DESC
LIMIT 50;

-- Equality columns first, then the sort column.
CREATE INDEX CONCURRENTLY orders_account_status_created_idx
    ON orders (account_id, status, created_at DESC);
```

With that index the plan walks the index in order, stops at 50 rows, and runs each subquery 50 times, not once per row in the table. The ORM can express all of this with `Subquery` and `OuterRef`. Where it could not express something cleanly, I used raw SQL, always with parameters and never with string formatting. `CONCURRENTLY` builds the index without blocking writes; in a Django migration that is `AddIndexConcurrently` in a migration with `atomic = False`.

## Keeping the count flat with a test

A prefetch is easy to undo by accident, so the last step is a test that fails when the count grows. I prefer comparing two sizes to pinning an exact number. A pinned number breaks every time someone adds a legitimate query. A comparison only breaks when the count starts to depend on the rows.

```python
from django.db import connection
from django.test import TestCase
from django.test.utils import CaptureQueriesContext


class OrderListQueryCountTest(TestCase):
    def count_list_queries(self):
        with CaptureQueriesContext(connection) as ctx:
            response = self.client.get("/api/orders/")
        self.assertEqual(response.status_code, 200)
        return len(ctx.captured_queries)

    def test_query_count_does_not_grow_with_rows(self):
        self.client.force_login(create_test_user())   # your factories
        make_orders(count=5, items_per_order=3)
        self.count_list_queries()                     # warm-up request
        few = self.count_list_queries()

        make_orders(count=45, items_per_order=3)
        many = self.count_list_queries()

        self.assertEqual(few, many)
```

The warm-up request matters. Sessions, translations and content types often load on the first request and come from a cache after that, so the first count can be one or two higher for reasons that have nothing to do with your queryset. Also make sure every optional relation is set on at least one row. A relation that is empty for every row can skip its prefetch query entirely, and then the count grows when real data arrives.

If you do want an exact number, `assertNumQueries` does that, and pytest-django has the `django_assert_num_queries` fixture. At Gainfront, query-count tests on list endpoints are part of the definition of done when I move a module onto our newer API conventions.

## Results

- **MarsDevs, N+1:** on the request paths I worked on, queries per request went from 500+ to roughly 5 to 10, by removing N+1 patterns with `select_related` and `prefetch_related` and fetching only the fields each response needed.
- **MarsDevs, slow SQL:** separately, the heaviest queries went from roughly 15 to 25 seconds to about 1 to 2, through ORM and raw SQL rewrites, better joins and subqueries, and indexes.
- **Gainfront report:** the certification columns went from N to 3N extra queries per report to zero extra queries, inside one SQL statement.

The honest caveats: these are the paths I fixed, not every endpoint in either codebase. I don't have clean before-and-after response times for the N+1 work, so I don't quote any, and the two MarsDevs numbers come from different changes.

## What I would do differently

- **Write the query-count test the day an endpoint ships,** not after it gets slow. It costs a dozen lines and catches most regressions in review.
- **Keep the queryset next to the serializer.** A classmethod on the serializer that returns its own optimized queryset means a new nested field and its `select_related` land in the same diff.
- **Check `loops=` on every subquery I add to a report.** The correlated subquery that fixes an N+1 on a page of 50 rows is the one that hurts inside a large `GROUP BY`.

The case I still don't have a clean answer for is one serializer reused by three endpoints with three different querysets. A count test on each endpoint catches the drift, but only on the endpoints someone remembered to test.
