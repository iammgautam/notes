Without evaluation, every RAG change is a guess: a new chunker, embedding model, prompt or LLM version may help some queries and silently break others. Evaluation turns "it feels better" into numbers you can track in CI. The key idea is to separate the pipeline into stages and measure each one, because a wrong answer has two very different causes: the right passage was never retrieved, or it was retrieved and the model ignored or distorted it.

## How it works

### Two layers of metrics

```text
query ──► retrieval ──► passages ──► generation ──► answer
              │                          │
     retrieval metrics:          generation metrics:
     recall@k, MRR, nDCG         faithfulness, answer relevance,
     (needs labeled relevant     correctness vs reference,
      chunks/documents)          refusal behavior
```

### Retrieval metrics

Given, per query, the set of relevant chunk (or document) ids:

| Metric | Definition | Use it for |
|---|---|---|
| `recall@k` | Fraction of relevant items found in the top `k` | Did the right context make it into the prompt? The primary RAG metric |
| `precision@k` | Fraction of top `k` that is relevant | Context noise and token waste |
| `hit@k` | 1 if any relevant item in top `k` | Single-answer questions |
| MRR | Mean of `1 / rank` of the first relevant item | How high the first good hit is ranked |
| nDCG@k | Rank-discounted gain with graded relevance | When relevance has levels (perfect, partial) |

Measure first-stage recall at a large `k` (for example `recall@50`) and final recall at the prompt size (`recall@5` after reranking). If `recall@50` is low, fix chunking, embeddings or hybrid search. If `recall@50` is high but `recall@5` is low, fix reranking.

Label at the document level when chunk boundaries change often; chunk-level labels break every time you re-chunk. A practical compromise: label a relevant document plus a short evidence quote, and count a chunk as relevant if it contains the quote.

### Generation metrics

- **Faithfulness (groundedness):** every claim in the answer is supported by the retrieved passages. This catches hallucination. Usually computed by splitting the answer into claims and checking each against the context with an LLM judge or an NLI model.
- **Answer relevance:** the answer addresses the question asked.
- **Correctness:** the answer matches a reference answer. Requires reference answers in the golden set; judged by an LLM or by exact match for short factual answers.
- **Citation accuracy:** cited passages actually support the cited sentences.
- **Refusal behavior:** for unanswerable questions, the system says it does not know instead of inventing.

### Golden sets

A golden set is a versioned list of queries with expected evidence and, ideally, reference answers:

```json
{
  "id": "refund-annual-45d",
  "tenant": "eval-tenant-1",
  "query": "Can I get a refund on an annual plan after 45 days?",
  "relevant_docs": ["policy/refunds.md"],
  "evidence": "Annual plans are refundable within 30 days",
  "reference_answer": "No. Annual plans are refundable only within 30 days.",
  "tags": ["billing", "negation"],
  "answerable": true
}
```

Sources for queries, in order of value: real user queries from logs (sampled, anonymized, with consent), questions from support tickets, queries written by domain experts, and synthetic queries generated by an LLM from your documents. Synthetic queries are cheap and good for coverage but tend to reuse the document's wording, which flatters vector search; mix in real phrasing.

Size: 50–100 queries catch large regressions; a few hundred give stable numbers per category. Include hard cases deliberately: exact identifiers, negation, multi-hop questions, unanswerable questions, and questions whose answer changed recently.

### LLM-as-judge

Using an LLM to grade answers scales evaluation, but judges have known biases:

| Bias | Effect | Mitigation |
|---|---|---|
| Position bias | Prefers the first (or second) answer in pairwise comparison | Swap order, run both, require agreement |
| Verbosity bias | Prefers longer answers | Rubric that penalizes unsupported detail |
| Self-preference | Rates outputs from its own model family higher | Use a different model family as judge |
| Leniency | Gives high scores by default | Binary or 3-point scales with explicit criteria |
| Nondeterminism | Scores drift between runs | Temperature 0, multiple samples, track variance |

Calibrate the judge: hand-label 50–100 examples, compute agreement with the judge, and adjust the rubric until agreement is acceptable. Re-check when you change the judge model. Prefer narrow binary questions ("Is claim X supported by passage Y? yes/no") over holistic 1–10 scores.

## In practice

### Retrieval metrics in a few lines

```python
def recall_at_k(retrieved: list[str], relevant: set[str], k: int) -> float:
    if not relevant:
        return 0.0
    return len(set(retrieved[:k]) & relevant) / len(relevant)

def reciprocal_rank(retrieved: list[str], relevant: set[str]) -> float:
    for i, doc_id in enumerate(retrieved, start=1):
        if doc_id in relevant:
            return 1.0 / i
    return 0.0

def evaluate_retrieval(cases, retrieve, k_values=(5, 20, 50)):
    rows = []
    for c in cases:
        if not c["answerable"]:
            continue
        got = [h.document_key for h in retrieve(c["query"], c["tenant"], k=max(k_values))]
        rel = set(c["relevant_docs"])
        rows.append({f"recall@{k}": recall_at_k(got, rel, k) for k in k_values}
                    | {"rr": reciprocal_rank(got, rel), "tags": c["tags"]})
    return rows   # aggregate overall and per tag
```

Aggregate per tag as well as overall. A change that improves the average and breaks every "negation" query is a regression.

### A faithfulness judge prompt

```text
You are checking whether an answer is supported by sources.

For each numbered claim, reply with SUPPORTED, CONTRADICTED or NOT_FOUND,
and the source id that supports it. Judge only against the sources below,
not your own knowledge.

<sources>...</sources>
<claims>
1. Annual plans are refundable within 30 days.
2. Refunds are processed within 5 business days.
</claims>
```

Faithfulness score = supported claims / total claims. Track the rate of answers with any `CONTRADICTED` claim separately; those are the dangerous ones.

### Regression testing in CI

```text
PR changes prompt / chunker / model / retrieval params
        │
        ▼
  run golden set (retrieval metrics: cheap, every PR)
  run generation judges (costly: nightly or on label "eval")
        │
        ▼
  compare to baseline stored from main
  fail if recall@5 drops > 2 pts, faithfulness drops > 3 pts,
  or any "critical" tagged case flips from pass to fail
```

Store per-case results, not just averages, so you can diff which queries changed. Pin the judge model and prompt; a judge change invalidates baselines.

> **In production:** Offline evals miss what users actually ask. Log retrieval ids and scores, collect thumbs up/down and "no answer" rates, and sample production traffic weekly into the golden set.

## Pitfalls

- **Only measuring final answers.** You cannot tell retrieval failures from generation failures. Fix: stage metrics.
- **Synthetic-only golden sets.** Inflated vector-search scores. Fix: mix in real queries.
- **Chunk-level labels that rot.** Re-chunking invalidates labels. Fix: document plus evidence-quote labels.
- **Uncalibrated judges.** Scores look precise and mean little. Fix: measure judge agreement with human labels.
- **Averages hiding regressions.** Fix: per-tag breakdown and per-case diffs.
- **Evaluating on one tenant's data with another tenant's ACLs.** Fix: dedicated eval tenants with fixed fixtures.

## Checklist

- Golden set in version control with ids, evidence, reference answers, tags and unanswerable cases.
- Retrieval metrics (`recall@k`, MRR) on every change; generation metrics on a schedule.
- LLM judges with binary rubrics, calibrated against human labels.
- Baselines stored per case; CI fails on threshold drops.
- Production feedback flows back into the golden set.

## Interview angle

- **How do you evaluate a RAG system?** Separate retrieval (recall@k, MRR against labeled relevant docs) from generation (faithfulness, correctness, refusal on unanswerable), using a golden set and calibrated LLM judges, run in CI.
- **What are the risks of LLM-as-judge?** Position, verbosity and self-preference bias, leniency and drift. Mitigate with binary rubrics, order swapping, a different model family and human calibration.
- **Recall@50 is high, answers are bad. Where do you look?** Reranking and prompt assembly first, then generation faithfulness.
